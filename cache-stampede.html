Solving Cache Stampedes with Double-Check Locking

How I achieved 6,800+ Requests Per Second and a P(95) of 0.66ms under a 1,000 VU stress test by synchronizing Kestrel minimal APIs with SemaphoreSlim and Dapper.

May 2026 6 min read View PoC Repo

When building high-traffic Business Intelligence (BI) dashboards, the backend API is frequently tasked with serving heavy aggregate views to hundreds of users simultaneously. While caching is the standard solution, implementing it incorrectly under massive concurrent load can lead to a devastating phenomenon known as a Cache Stampede.

The Challenge: Connection Pool Exhaustion

During peak load, if a popular cache key expires (or on cold start), multiple concurrent requests will experience a cache miss simultaneously. Instead of one request querying the database and repopulating the cache, every single concurrent request hits the database at the same time.

In my initial implementation, a surge of 1,000 concurrent Virtual Users (VUs) resulted in the database connection pool immediately exhausting, leading to cascading timeouts and severe thread pool starvation in ASP.NET Core.

The Solution: Lookaside Cache with Double-Check Locking

To serialize database access for identical requests, I introduced a Double-Check Locking pattern synchronized via an asynchronous semaphore (SemaphoreSlim). This ensures that only the first request performs the expensive database query, while the remaining concurrent requests wait for the cache to be populated and then read directly from memory.

Here is the sanitized core mechanism I used:

private static readonly ConcurrentDictionary<string, SemaphoreSlim> _locks = new();

public async Task<T> GetOrCreateAsync<T>(string cacheKey, Func<Task<T>> factory)
{
    // First Check: Fast path, read from cache
    if (_cache.TryGetValue(cacheKey, out T cachedValue))
    {
        return cachedValue;
    }

    // Cache Miss: Acquire the lock specific to this key
    var keyLock = _locks.GetOrAdd(cacheKey, _ => new SemaphoreSlim(1, 1));
    await keyLock.WaitAsync();

    try
    {
        // Second Check: The cache might have been populated while waiting for the lock
        if (_cache.TryGetValue(cacheKey, out cachedValue))
        {
            return cachedValue;
        }

        // Only one thread per key executes the factory (DB Query)
        var value = await factory();
        
        // Populate cache
        _cache.Set(cacheKey, value, TimeSpan.FromMinutes(5));
        
        return value;
    }
    finally
    {
        keyLock.Release();
    }
}

Optimizing the Data Layer with Dapper

To complement the locking mechanism, I swapped Entity Framework Core for Dapper. By using Dapper alongside Kestrel's Minimal APIs, I bypassed the heavy ORM overhead, enabling raw SQL execution with zero-allocation object mapping.

Key Takeaways

  1. Lock Granularity is Crucial: Locking on a per-key basis (via ConcurrentDictionary<string, SemaphoreSlim>) prevents unrelated requests from blocking each other.
  2. Always Double-Check: The secondary cache check inside the lock is mandatory. Without it, queued threads will still execute the database query after acquiring the lock.
  3. Disable Blocking Loggers: Under extreme load, console logging in ASP.NET Core can become a bottleneck. I stripped out unnecessary loggers in the production environment.
