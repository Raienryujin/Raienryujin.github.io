Architecting an Atomic Monorepo: Project Forge

How I eliminated integration drift and redundant CI builds by designing an enterprise monorepo template with path-filtered GitHub Actions and shared TypeScript contracts.

May 2026 5 min read View Project Forge Repo

When engineering features that cross-cut across a frontend UI, backend API, and shared logic, the traditional polyrepo approach starts to severely damage developer velocity. Dealing with multiple repositories often leads to a cycle of updating shared type definitions in one repo, publishing them, updating the API in another repo, and finally integrating those changes in a frontend repo.

The Challenge: Friction and Integration Drift

Managing a full-stack architecture across separate repositories introduces several pain points:

  • Integration Drift: API contracts and UI components easily fall out of sync when updated in separate pull requests.
  • Redundant CI Builds: A simple documentation update in a polyrepo might trigger a heavy Docker build process.
  • Complex Code Reviews: Reviewing a single feature requires jumping between multiple PRs across different codebases.

The Solution: An Atomic Full-Stack Monorepo

To eliminate these bottlenecks, I designed Project Forge — a production-grade monorepo template. By co-locating the backend, frontend, shared packages, infrastructure configurations, and CI/CD pipelines in a single repository, the architecture shifts from fragmented components to a cohesive, unified system.

This allows for atomic full-stack commits. Instead of coordinating multiple pull requests across different repositories, a single commit can introduce an ASP.NET Core API endpoint, a Next.js UI component, and the shared TypeScript type definition that binds them together. One pull request. One review cycle. One seamless deployment.

The Monorepo Philosophy

Transitioning to a monorepo isn't just about moving files into the same folder; it requires a deliberate architectural philosophy to prevent the repository from becoming a tangled monolith. Key principles include:

  • Unified Tooling & Code Sharing: Shared logic, such as TypeScript interfaces, validation schemas, and UI components, are extracted into isolated, internal packages. This ensures the frontend and backend consume the exact same source of truth, eliminating silent integration failures.
  • Enforced Boundaries: By strictly separating applications (e.g., the API and the Web app) from reusable packages, the architecture maintains high cohesion and low coupling. Applications consume packages, but packages never depend on applications.
  • Developer Velocity: A standardized development environment means any engineer can clone the repository, run a single command, and spin up the entire distributed system locally. There's no need to piece together different services or configure complex network routing between local repositories.

Path-Filtered CI/CD Pipeline

One of the biggest concerns with monorepos is that changing a single file can trigger a massive CI pipeline that rebuilds every project in the repository. To solve this, I implemented a path-filtered CI strategy using GitHub Actions.

The pipeline analyzes the Git diff and selectively triggers jobs based on the paths that were modified. To enforce branch protection rules cleanly, it uses a ci-gate aggregator job that provides a single, consistent status check.

Push to main/develop or PR opened
│
├─── Files changed in apps/api/** or .github/workflows/**
│    └── ✅ Trigger build-api job
│        • dotnet restore → build → test
│
├─── Files changed in apps/web/** or .github/workflows/**
│    └── ✅ Trigger build-web job
│        • npm ci → lint → build
│
└─── ci-gate (aggregator)
     └── Reports overall pass/fail for branch protection

Key Takeaways

  1. Atomic Commits Boost Velocity: Being able to enforce contract changes and implement them in the UI in a single PR drastically reduces integration errors.
  2. Smart CI is Mandatory: Without path-filtering, a monorepo quickly becomes a CI bottleneck. The `ci-gate` pattern is essential for reliable branch protection.
  3. Unified Tooling: Sharing ESLint configs, Prettier rules, and TypeScript interfaces across `apps/web` and `packages/ui` ensures a consistent codebase.
