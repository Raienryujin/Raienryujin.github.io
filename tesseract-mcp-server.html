Tesseract: MCP Codebase Graph Server

How I built a local SQLite codebase graph indexer to slash AI agent context consumption by replacing bulk file-reads with precise, context-aware AST queries.

April 2026 6 min read

Have you ever watched an AI coding assistant read a 4,000-line source file just to answer a simple question like, "What does this class depend on?" It’s painful. It’s slow. And worse, it consumes token budgets like a teenager at an all-you-can-eat buffet.

Modern AI agents are incredibly smart, but they are also context-hungry beasts. When we give them access to raw files, we dump the entire contents of a file into their context window. If the agent needs to inspect five files, you’ve suddenly blown through 20,000 tokens—all for a task that should have taken a fraction of that. I built Tesseract to solve this exact problem.

"Feeding raw files to an LLM to find a method signature is like printing out the entire library catalog just to find which shelf has the fiction books."

The Architectural Goal: Precise Graph Queries

Instead of feeding raw source code to the LLM context window, Tesseract operates under a simple philosophy: Query the graph, not the files.

Tesseract runs locally and maintains a lightweight SQLite database structured as an AST (Abstract Syntax Tree) graph. Every meaningful code entity—classes, functions, methods, and imports—is indexed as a node. Every structural relationship—calls, inheritance, and imports—becomes an edge.

By exposing these entities to AI agents via the Model Context Protocol (MCP), they can invoke precise tools. Here's a quick comparison of the efficiency gain:

  • The Old Way: "Read user_service.py" → ~4,000 tokens consumed.
  • The Tesseract Way: "What does UserService depend on?" → 3 edges, ~200 tokens consumed.

Key Design Principles

  1. Token Efficiency First: Every query returns only the minimal subgraph needed, never raw file contents. We keep the LLM focused on context rather than scanning boilerplate code.
  2. Incremental Indexing: We calculate cryptographic file hashes to detect modifications. If you modify one file in a 500-file project, Tesseract only re-parses and updates that single file in the graph, saving local CPU cycles.
  3. Graph-First Schema: Relational databases aren't traditionally friendly to graph operations, but by structuring clean Entity (Node) and Relationship (Edge) schemas, traversal queries like "What calls this function?" or "What does this class inherit from?" execute in milliseconds.
  4. TDD at the Core: Writing database queries can get messy quickly. I wrote the pytest suite alongside (and often prior to) implementing the CRUD repository methods. This ensured that model validation and relationship constraints were flawless before the database was ever wired to a parser.

What's Next?

My next immediate milestone is fleshing out the AST parser layer with tree-sitter to fully index Python codebases, followed by setting up the asynchronous JSON-RPC-based transport layer for the Model Context Protocol. The foundation is set, and the tests are green—now it's time to build the bridge to the LLM!
